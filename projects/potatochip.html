프로젝트 소개

맛에는 문제가 없지만 크기나 모양이 기준에 못 미쳐 팔리지 못하는 농산물이 많습니다. 이런 농산물을 농가가 중간 유통 없이 소비자에게 직접 파는 온라인 장터입니다. 교육 과정의 팀 프로젝트로 개발했습니다.

내 역할

팀장으로 일정과 협업 방식을 정하면서, 상품 등록·검색·장바구니 기능을 직접 만들었습니다.

  • 상품 기능 상품 등록·수정·삭제, 본인 상품만 고칠 수 있는 권한 검사, 카테고리·검색어로 찾는 기능을 만들었습니다.
  • AI 등록 도우미 사진만 올리면 AI가 사진을 보고 상품 제목과 설명 초안을 대신 써 주는 기능을 붙였습니다.
  • 장바구니 담은 순간의 가격을 그대로 유지하는 구조를 만들었습니다. 제 작업 범위는 여기까지이고, 주문·결제는 다른 팀원이 이어받았습니다.
  • 부가 기능 직접 수령할 위치를 지도로 보여 주는 기능과, 기간별로 많이 팔린 상품 순위를 집계하는 기능을 만들었습니다.
  • 팀 리딩 각자 작업한 코드를 겹치지 않게 합치는 규칙을 정하고, 서로 코드를 확인한 뒤 합치도록 운영했습니다. 일정과 문서도 총괄했습니다.

상품 등록과 검색

농가가 상품을 올리고, 구매자가 원하는 조건으로 찾아 들어오는 구간입니다.

사진 올리기› AI가 제목·설명 초안 작성› 판매자 확인 후 등록› 카테고리·검색어로 찾기› 수령 위치 지도
  • 판매자 대부분이 농가라, 상품 설명을 쓰는 단계에서 등록을 포기하는 경우가 많았습니다. 사진만 올리면 AI가 사진을 보고 제목과 설명 초안을 채워 주고, 판매자는 확인하고 고치기만 하면 되도록 만들었습니다.
  • AI가 쓴 글은 초안일 뿐이라 바로 저장하지 않고 입력창에 채워만 둡니다. 판매자가 고친 내용이 항상 우선입니다.
  • 본인 상품만 수정·삭제할 수 있게 막았습니다. 화면에서 보내오는 "나는 판매자다"라는 정보는 조작될 수 있어 믿지 않고, 로그인한 사람과 저장된 상품 주인을 서버에서 직접 대조합니다. "판매자인가"와 "이 상품의 주인인가"는 다른 질문이라 두 가지를 따로 검사합니다.
  • 구매자는 작물 종류와 산지로 찾는 경우가 많아, 카테고리와 검색어를 함께 걸 수 있는 필터를 만들었습니다.
  • 직접 찾아가 받는 거래가 많아 지도 서비스를 연결해 상품별 수령 위치를 지도로 보여 줍니다.
  • 화면 수가 많지 않고 검색 포털에 잘 노출돼야 해서, 서버가 화면을 직접 그려 보내는 방식을 골랐습니다.

확인한 것과 남은 한계

  • 확인 방법 위에 있는 테스트 계정으로 로그인해 다른 판매자의 상품을 고치려고 하면 서버가 거부합니다.
  • 미검증 비로그인 상태나 관리자 계정까지 포함한 모든 경우를 자동 테스트로 고정해 두지는 않았습니다. 다음 과제입니다.
  • 한계 AI 초안 만들기가 실패하면 빈 입력창이 뜨는데, 다시 시도하라는 안내는 넣지 않았습니다.

장바구니 — 담아 둔 금액이 바뀌던 문제

상황

장바구니가 상품의 현재 가격을 그때그때 가져오는 방식이었습니다. 그래서 구매자가 담아 둔 사이에 판매자가 가격을 올리면, 장바구니에서 본 금액과 실제 결제 금액이 달라졌습니다.

해결

장바구니에 담는 순간의 가격을 사진 찍듯 따로 저장해 두고, 합계와 주문 금액을 모두 그 값으로 계산하게 바꿨습니다.

결과

판매자가 가격을 바꿔도 이미 담긴 상품의 금액은 그대로입니다. 장바구니에 보이는 금액과 결제 단계로 넘어가는 금액이 어긋나지 않습니다.

구현 상세

장바구니에 담기› 그 시점 가격 따로 저장› 합계 금액 계산› 주문 단계로 전달
  • 상품 가격을 그때그때 불러오면 변경에 그대로 끌려갑니다. 그래서 장바구니 항목이 담은 시점의 금액을 자기가 직접 들고 있도록 만들었습니다.
  • 제 작업 범위는 장바구니 합계 계산까지이고, 이후 주문·결제는 이 저장된 금액을 그대로 받아 쓰도록 형식을 맞춰 넘겼습니다. 구조는 팀과 함께 정하고, 실제 구현은 제가 했습니다.
  • 합계 금액은 서버에서 다시 계산합니다. 화면에서 보내온 금액을 그대로 믿으면 값을 조작해 싸게 살 수 있기 때문입니다.

남은 한계

  • 정책 미정 장바구니에 몇 달씩 담겨 있던 상품의 가격을 언제까지 지켜 줄지, 품절된 상품을 주문 단계에서 어떻게 처리할지는 아직 정하지 않았습니다. 저장한 금액에 유효기간을 두는 방향으로 검토 중입니다.
  • 한계 가격이 바뀌었다는 표시가 없어, 담아 둔 금액과 지금 판매가가 다르다는 사실이 구매자에게 보이지 않습니다.

팀 리딩 — 코드가 사라지던 문제

상황

여러 명이 같은 프로젝트를 고칠 때는 각자 복사본에서 작업한 뒤 원본에 합칩니다. 그런데 팀원들이 기능을 다 끝낼 때까지 합치지 않고 미뤘습니다. 오래 들고 있던 작업이 한꺼번에 올라오니 같은 파일을 서로 다르게 고친 충돌이 대량으로 났고, 급하게 정리하다 다른 팀원의 코드가 덮여 사라지는 일까지 있었습니다.

해결

합치는 단위를 기능 하나 크기로 잘게 쪼개고, 작업을 시작하기 전과 합치기 직전에 원본의 최신 내용을 먼저 받아 오도록 규칙을 세웠습니다. 여러 명이 함께 건드리는 파일은 담당자를 정해 한 사람에게 모으고, 올라온 요청은 그날 안에 확인하고 합쳐 작업이 오래 묵지 않게 했습니다.

결과

충돌이 마지막에 몰리지 않고 각자 작업하는 중에 미리 드러나 푸는 시간이 줄었고, 합친 뒤 기능이 사라지는 사고도 없어졌습니다. 이후 프로젝트에도 같은 방식을 그대로 썼습니다.

구현 상세

  • 기능 하나마다 작업 공간을 따로 만들고, 원본에는 확인 요청을 거쳐야만 합칠 수 있게 했습니다.
  • 합치기 전에 최신 내용을 먼저 받아 오게 해서, 충돌은 확인하는 사람이 아니라 코드를 쓴 본인이 자기 작업 공간에서 풀도록 했습니다.
  • 여러 명이 건드리는 공통 파일은 담당자 한 명에게 변경을 모으고, 5인의 일정과 진행 상황을 문서로 공유하며 기능별 담당을 나눴습니다.

배포 — 어디까지 했는지

  • 상품 사진은 개발 중에는 내 컴퓨터에, 실제 서비스에서는 아마존 파일 보관소(S3)에 저장하도록 나눴습니다. 서버 안에 직접 보관하면 서버를 다시 띄울 때 사진이 사라지거나, 서버가 여러 대일 때 서로 보이지 않기 때문입니다.
  • 프로그램과 실행 환경을 통째로 묶어(Docker) 클라우드 서버 한 대에 올렸습니다. 서버 1대 운영이며, 접속이 몰릴 때 여러 대로 나눠 받는 구성은 적용하지 않았습니다.
  • 미측정 서버 1대가 몇 명까지 감당하는지 재 보지 않아, 언제 서버를 늘려야 할지는 아직 판단하지 않았습니다.
