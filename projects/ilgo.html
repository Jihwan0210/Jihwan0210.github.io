프로젝트 소개

고지서, 안내문, 행정 문자는 용어가 어려워 무엇을 해야 하는지 알기 힘듭니다. 사진 한 장만 찍으면 AI가 쉬운 말로 풀어 주고, 놓치면 안 되는 것과 해야 할 일까지 알려 주는 앱입니다. 한국어가 익숙하지 않은 외국인과 고령자를 위해 만들었고, AI Re-Local 해커톤 출품작입니다.

내 역할

앱 화면은 다른 팀원이 만들고, 저는 화면 뒤에서 실제 일을 하는 서버 전체를 맡았습니다. 로그인 처리, AI에 문서를 보내 결과를 받아 정리하는 과정, 앱과 주고받을 형식 정하기, 테스트까지 담당했습니다.

  • 로그인 처리 로그인한 사람에게 출입증 같은 토큰을 주고, 요청이 올 때마다 이 출입증을 확인해 기능별로 접근을 허용하거나 막습니다.
  • 문서 분석 사용자가 올린 사진을 AI에 보내고, 돌아온 답을 설명 · 위험도 · 핵심 내용 · 해야 할 일 네 칸으로 정리해 앱에 넘깁니다.
  • 요청 처리 사진 파일과 이미 글자로 된 요청을 모두 받을 수 있게 하고, 지난 분석 기록은 스크롤을 내려도 느려지지 않는 방식으로 불러옵니다.
  • 데이터베이스 데이터 보관은 직접 서버를 세우는 대신 관리형 서비스(Supabase)를 빌려 썼습니다. 4일뿐인 대회에서 서버 설치에 시간을 쓰지 않고 기능 개발에 집중하기 위한 선택입니다.
  • 안정성 오류가 났을 때 돌려주는 형식을 하나로 통일하고, 한 사람이 AI를 너무 자주 부르지 못하게 막고, 테스트 코드로 기능이 깨지지 않는지 확인했습니다.

왼쪽에서 오른쪽으로 요청이 흘러갑니다. 색이 들어간 칸이 제가 맡은 부분입니다.

AI 문서 분석 — 답변 형태가 매번 달라지던 문제

상황

AI는 사람에게 말하듯 자유롭게 글로 답합니다. 같은 고지서를 넣어도 어떤 때는 줄글로, 어떤 때는 목록으로 나왔습니다. 형태가 매번 달라지니 앱에서는 화면을 어떻게 만들어야 할지 정할 수 없었습니다.

해결

앱에 넘기기 전에 서버에서 형태를 고정했습니다. AI 답을 설명 · 위험도 · 핵심 내용 · 해야 할 일 네 칸으로 정리하고, 정리에 실패하더라도 정해진 오류 형식으로 내려가게 했습니다.

결과

앱은 정해진 한 가지 형식만 보고 화면을 만들면 됐습니다. 주고받을 내용을 문서로 미리 공유해, 4일 동안 서버와 앱을 동시에 개발할 수 있었습니다.

구현 상세

문서 사진› 로그인 확인› AI에 분석 요청› 네 칸으로 정리› 기록 저장 · 조회
  • AI 답변을 설명 · 위험도 · 핵심 내용 · 해야 할 일 네 칸으로 나눠, 앱이 곧바로 화면에 그릴 수 있는 형태로 내려줍니다.
  • 즉석에서 사진을 찍어 올리는 경우와, 이미 글자로 옮겨진 내용을 보내는 경우가 모두 있어 두 가지 요청 방식을 지원했습니다.
  • 분석 기록은 계속 쌓이기만 합니다. 목록을 불러올 때 "앞에서부터 몇 개 건너뛰기" 방식은 뒤로 갈수록 느려져서, "마지막으로 본 지점부터 이어서" 가져오는 방식을 골랐습니다.

확인한 것과 남은 한계

  • 확인함 AI 답변에 필요한 항목이 빠져 있거나 형식이 어긋나면 실패로 처리되고, 앱에는 정해진 오류 형식이 내려갑니다. 앱이 이상한 화면을 그리지 않습니다.
  • 한계 정리에 실패했을 때 AI에 다시 물어보는 기능은 없습니다. 실패한 사례를 모아 요청 문구와 형식을 다듬는 쪽으로 남겨 뒀습니다.
  • 미측정 목록 조회 방식은 구조상 더 낫다고 판단해 고른 것이며, 데이터가 많이 쌓인 상태에서 두 방식의 속도를 직접 비교하지는 않았습니다.

로그인과 공통 규칙 — 기능마다 제각각이던 문제

상황

기능을 추가할 때마다 로그인 확인 방식과 오류 메시지 형식이 기능마다 조금씩 달라졌습니다. 앱에서는 기능별로 다르게 처리해야 했습니다. 또 AI 호출에 제한이 없어, 한 사람이 계속 눌러 대면 비용을 막을 방법이 없었습니다.

해결

기능마다 하던 검사를 입구 한곳에 모았습니다. 모든 요청은 들어오자마자 로그인 여부를 확인받고, 오류 형식과 호출 횟수 제한도 같은 자리에서 일괄 적용됩니다.

결과

기능을 새로 추가해도 로그인 확인과 오류 형식이 자동으로 같게 적용됩니다. 테스트 코드를 만들어 두어, 코드를 고쳤을 때 기존 기능이 깨지지 않았는지 바로 확인할 수 있습니다.

구현 상세

  • 로그인한 사람에게 출입증(토큰)을 발급하고, 요청이 올 때마다 이 출입증을 확인합니다. 서버가 누가 접속 중인지 따로 기억해 두지 않아도 되는 방식입니다.
  • 어떤 기능에서 오류가 나든 같은 형식으로 내려보내 앱이 한 가지 방법으로 처리하게 했습니다. 한 사람이 1분에 20번까지만 AI를 부를 수 있게 제한했습니다. 20회는 서비스에서 정한 기준값이며, 성능을 측정해 나온 숫자가 아닙니다.
  • 서버와 앱이 주고받을 내용을 자동으로 문서화해 팀에 공유했습니다. 앱 담당자가 서버 완성을 기다리지 않고 동시에 작업할 수 있었습니다.
  • 로그인 실패, 횟수 초과, AI 응답 정리 실패 같은 상황을 자동으로 검사하는 테스트 코드를 만들어, 코드를 고칠 때마다 확인했습니다.

선택 근거와 남은 한계

  • 선택 이유 서버가 접속자를 직접 기억하는 방식은, 나중에 서버를 여러 대로 늘릴 때 기억한 내용을 서로 공유할 장치가 따로 필요합니다. 4일짜리 일정에서 그런 장치 없이 입구에서 검사만으로 끝낼 수 있어 출입증 방식을 골랐습니다. 두 방식의 속도를 직접 비교 측정한 것은 아닙니다.
  • 한계 한 번 발급한 출입증은 유효기간이 끝나기 전까지 서버가 강제로 무효화할 수 없습니다. 출입증을 주기적으로 바꿔 주고 도난을 감지하는 방식은 검토만 했고 구현하지 않았습니다.
  • 한계 호출 횟수는 서버 한 대의 기억을 기준으로 셉니다. 서버를 여러 대로 늘리면 대수만큼 한도가 늘어나는 셈이라, 공용 저장소로 옮기는 것이 다음 과제입니다.
